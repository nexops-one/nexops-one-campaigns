# Access control and audit log

Every API request is made by a **principal**: a user, a token, or the engine
itself. A principal is bound to one tenant workspace and holds one or more
**roles** there. Every endpoint requires one **permission**, listed as
`x-permission` in the OpenAPI definition (`/api/v1/openapi.yaml`). A request
whose roles do not grant it is refused with `403 forbidden` and the missing
`permission`.

## Roles and permissions

The roles (`auditor`, `owner`, `reviewer`, `approver`, `admin`) and the
permission matrix are generated from the code: see
[reference/roles.md](reference/roles.md). Roles are additive: a principal is
allowed what any of its roles allows. The `evidence.*` and `workflow.*`
permissions are used by the review workflow. `report.generate` stores a new
report (see [reports.md](reports.md)); reading, downloading and regenerating
reports only need `data.read`.

## Users and members

Users belong to one tenant and are identified by their email address (stored in
lower case). A **member** is a user holding roles in one workspace. Passwords are
stored as argon2id hashes and are only generated by the engine, never chosen on
the command line:

```bash
compliance-engine user create --tenant acme --email ann@example.com --workspace ws-1 --role owner+approver
compliance-engine user reset-password --tenant acme --email ann@example.com
```

Admins manage members through `PUT /api/v1/members/{email}` (roles) and
`DELETE /api/v1/members/{email}`. A workspace always keeps at least one admin
member (`409 last_admin`). Removing a member revokes that user's tokens in the
workspace.

## Tokens

| Kind | Where | Acts as | Roles |
|---|---|---|---|
| Static | `COMPLIANCE_TOKENS` | `token:<hash prefix>` | listed after the workspace (`:owner+auditor`), default `owner+admin` |
| User token | database | its user (`user:<id>`) | the roles it was issued with **that the user still holds**; shrinking a membership shrinks the token on the next request |
| Service token | database | `token:<id>` | only `owner` and/or `auditor`: a service token can never review or approve |

Rules:

- Anyone may create a token for themselves (`POST /api/v1/tokens`) with roles they hold (`403 role_not_held` otherwise).
- Only admins create service tokens (`"service": true`), list every token of the workspace, and revoke other callers' tokens.
- Token values are returned once and never stored; the database keeps SHA-256 hashes. Expired and revoked tokens are refused.
- Operators create tokens with `compliance-engine token create` (see [server.md](server.md)).

## Rate limits

- Each authenticated caller has a token bucket of `COMPLIANCE_RATE_BURST` requests refilled at `COMPLIANCE_RATE_LIMIT` per minute. An empty bucket answers `429 rate_limited` with `Retry-After` (seconds).
- Failed authentications are counted per client address (`COMPLIANCE_AUTH_FAILURE_LIMIT` per minute). When the budget is spent, **every** request from that address gets 429 until it refills, including requests with a valid token. Forwarding headers are not trusted: behind a reverse proxy all clients share the proxy's address, so raise the limit there or rate limit at the proxy.
- Buckets live in each server process; with several replicas each enforces its own limits.

## Console sessions

Users with a password sign in to the web console at `/console` ([console.md](console.md)).
A session is bound to one workspace of the user's tenant and its roles are
re-read from the membership on every request, like user tokens. Sessions end
after `COMPLIANCE_SESSION_IDLE` without activity (default 30 minutes) or
`COMPLIANCE_SESSION_MAX` after sign-in (default 12 hours). Failed sign-ins draw
on the same per-address failure budget as API authentication.

## Audit log

Every privileged action is recorded in an append-only, hash-chained audit log:
see [audit.md](audit.md).
