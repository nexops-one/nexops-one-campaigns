# Upgrading

Versions follow semantic versioning. Within a major version, the API
(`/api/v1`), the canonical schema versions already published, catalog
versions already shipped and stored data stay readable.

## Steps

1. Read the release notes for migrations and configuration changes.
2. **Back up** the database and keep the KEK ([backup-restore.md](backup-restore.md)).
3. Verify the new release (checksums and signatures: [install.md](install.md)).
4. Apply the migrations:
   - automatically: start the new version with `COMPLIANCE_AUTO_MIGRATE=true` (default). Migrations run under an advisory lock, so several replicas can start together;
   - or explicitly, before switching: `compliance-engine migrate status`, then `compliance-engine migrate up` with the table owner's credentials, and run the servers with `COMPLIANCE_AUTO_MIGRATE=false` (they refuse to start on a schema with pending migrations).
5. Start the new version and check `GET /api/v1/about`, `compliance-engine audit verify --tenant <id>`, and a report regeneration (`POST /api/v1/reports/{id}/regenerate`) of a recent report.

## Rolling back

`compliance-engine migrate down --yes <n>` reverts the last `n` migrations.
`down` of the audit-log migration refuses to run while events exist unless
`--force-drop-audit` is given; prefer restoring the backup taken in step 2.

## Generated documents and data

- Reference documents in `docs/reference` match the binary that generated them (`compliance-engine docs gen`).
- Reports are immutable. A report generated by an older version regenerates identically only with the engine version recorded in it; the regeneration result says which part differs.
- New catalog versions are added beside the old ones; stored evaluations keep the versions they used.
